Le test manuel du flow GitHub OAuth par l'utilisateur (credentials réels fournis) a révélé deux problèmes non détectés par les vérifications automatisées ci-dessus :

Impact : suppression complète de Prisma (`prisma/`, `generated/`, `src/prisma/`, deps `@prisma/*`/`pg`), ajout de `firebase-admin` + `FirestoreModule`/`FirestoreService` (`src/firestore/`), modèle `User` local (`src/users/user.model.ts`), réécriture de `AuthService`/`JwtStrategy`/`AuthController` sur des requêtes Firestore (collection `users`). BullMQ/Redis conservés pour la queue (décision explicite). spec.md §1 et plan.md mis à jour en conséquence.
- [x] **T1.8** — **Bug corrigé : callback OAuth ne créait jamais l'utilisateur en base.** `GoogleStrategy`/`GithubStrategy` ne renvoient que `{ email }` (pas d'id/plan), et le contrôleur signait directement le JWT à partir de ce payload incomplet → token sans `sub`, rejeté par `/auth/me` (d'où l'erreur "Connexion impossible." côté frontend). Fix : `googleCallback`/`githubCallback` appellent désormais `authService.findOrCreateOAuthUser(email, provider)` (upsert Firestore) avant d'émettre la session.
- [x] **T1.9** — Parcours GitHub OAuth validé de bout en bout par l'utilisateur, credentials Firebase réels renseignés dans `apps/api/.env` : autorisation GitHub → callback → utilisateur créé dans Firestore (collection `users`, projet `adddemo-bfd9d`) → redirection frontend → session active (page d'accueil affiche l'email connecté).

**Point ouvert (non bloquant)** : le projet Firebase utilisé (`adddemo-bfd9d`) est en région `asia-southeast1`, alors que le PRD impose un hébergement UE (RGPD). À corriger avant mise en production (nouveau projet Firebase en région EU, ou reconfiguration) — sans impact sur le développement local en cours.

**Non couvert / limites connues** :

- Pas de limite de taille explicite sur l'upload (`fileBase64` en `IsString` simple) — un certificat/keystore fait quelques Ko à quelques centaines de Ko en pratique, donc non bloquant pour le MVP, mais à durcir avant prod (`class-validator` `@MaxLength` ou limite au niveau du `ValidationPipe`/reverse proxy).

**Bugs découverts et corrigés pendant cette vérification** :
- **Permission GitHub App manquante** : écrire dans `.github/workflows/` exige la permission App **`workflows: write`**, distincte de `contents: write` (déjà accordée en Phase 2). Erreur GitHub explicite (`x-accepted-github-permissions`) ayant permis le diagnostic. Correction **hors code** : l'utilisateur a ajouté la permission dans les settings de `mobileflow-pkgr` puis accepté la mise à jour de permissions sur l'installation existante (étape séparée de la sauvegarde des settings de l'App, comme pour le souci de Setup URL en Phase 2 — cf. tasks.md Phase 2).
- **`workflow_dispatch` sur une branche sans le fichier workflow** : `ensureWorkflowInstalled` ne poussait le fichier que sur la branche par défaut (`branch` omis dans `createOrUpdateFileContents`) ; GitHub exige que le fichier workflow existe **sur la branche ciblée par le dispatch elle-même** (erreur `422 "Workflow does not have 'workflow_dispatch' trigger"` sur toute branche autre que la branche par défaut). **Non couvert / limites connues** :

Le job `build-ios` reste donc un squelette non signé tant que cet endpoint n'existe pas.
- **Pas de déclenchement automatique sur push** (FR-6) : nécessiterait le webhook GitHub (cf. ci-dessus) ou une autre source d'événement ; `autoTriggerBranch` n'a toujours pas de nouvel emplacement de persistance (point ouvert depuis la Phase 3).

- **Build orphelin possible** : si `dispatchWithRetry` échoue après ses 5 tentatives (ex. panne GitHub prolongée), le `Build` Firestore déjà créé reste bloqué au statut `queued` avec `githubRunId: null`, sans nettoyage automatique ni retry ultérieur — l'utilisateur devrait relancer un nouveau build manuellement.

## Correctifs post-vérification (test réel d'un build Android sur pwademo, après T5.17-T5.20)

L'utilisateur a relancé un vrai build Android sur `pwademo` avec le workflow corrigé (T5.15). Deux erreurs Gradle distinctes ont été rencontrées et corrigées, l'une après l'autre :

N'est pas un problème de configuration du workflow (se reproduirait en local) — corrigé en amont, côté génération du projet Android, plutôt que dans le workflow de build : nouvelle étape "Patch Android Gradle" dans `setup-workflow-template.ts`, exécutée juste après `npx cap add android` (conditionnée à `add_android == 'true'`), qui ajoute un bloc `configurations.all { exclude group: 'org.jetbrains.kotlin', module: 'kotlin-stdlib-jdk7' / 'kotlin-stdlib-jdk8' }` à la fin de `android/app/build.gradle` si le marqueur `kotlin-stdlib-jdk7` n'y est pas déjà présent (idempotent, applicable même si le workflow de setup est relancé).
